# Database Schema — AI Stock Analysis & Google OAuth

**Owner:** Yong Wee (Person 1)

Two features' worth of schema. The two tables that back the AI analysis feature are defined in `server/src/db/schema.sql` (and originally introduced by `server/src/db/migrations/011_add_ai_analysis_history.sql`, `012_add_ai_analysis_title.sql`, and `013_add_ai_preferences.sql`). "Sign in with Google" doesn't add a new table — it extends the shared `users` table (see `server/src/db/migrations/014_add_google_oauth.sql`). All three reference/live on `users(id)`, which is shared infrastructure — its `id`/`email`/`password_hash`/`google_id`/`name`/`avatar` columns are owned by this feature's auth half (Person 1), while `is_active`/subscription columns belong to Person 2's paywall. Column names below are the raw SQL names; the API layer aliases them to camelCase (e.g. `analysis_text` → `analysisText`).

## Tables I own

| Table | Purpose |
|---|---|
| `ai_analysis` | One row per "Analyze with AI" run — the shortlisted stocks sent to the model, the resulting write-up/comparison, and a renameable title. |
| `ai_preferences` | One row per user — their saved model tier / persona / detail level / custom instructions for future analysis runs. |

---

### `ai_analysis` — saved AI analysis runs

Backs the AI Analysis History page. A run is created by `POST /api/ai/analyze` (best-effort — a save failure doesn't fail the request) and can be renamed or have its text edited/deleted afterwards.

| Column | Type | Null | Key | Notes |
|---|---|---|---|---|
| `id` | CHAR(36) | No | PK | UUID, generated by the app (`randomUUID()` in `aiHistory.service.js`), not `DEFAULT (UUID())` |
| `user_id` | CHAR(36) | No | FK → `users(id)`, INDEX (part of composite) | Owner of the run |
| `title` | VARCHAR(200) | No | | Auto-generated from the shortlisted stock codes at save time (e.g. `"D05, O39, U11"` or `"D05, O39 +3 more"`), renameable via `PATCH /api/ai/history/:id`. Added in migration 012; backfilled for pre-existing rows as `"AI Analysis - <created_at>"`. |
| `stocks` | JSON | No | | The shortlisted stocks sent to the model — `[{exchangeCode, stockCode, stockName, values?}, ...]`. Kept so history can show what was analyzed without re-joining live screener data. |
| `analysis_text` | MEDIUMTEXT | No | | The model's output. For single-mode runs, plain text. For comparison-mode runs (2+ stocks), a `JSON.stringify`'d `{stocks, criteria, summary, disclaimer}` object stored as text in the same column — detected on read by attempting `JSON.parse`, so no schema change was needed to add comparison mode. Editable by the user afterwards (not re-derived from the model on edit). |
| `created_at` | TIMESTAMP | No | | `DEFAULT CURRENT_TIMESTAMP`; drives the latest-first ordering on the history page |

- **Primary key:** `id`.
- **Foreign key:** `user_id` → `users(id)` `ON DELETE CASCADE` (deleting a user's account removes their AI analysis history).
- **Index:** `idx_ai_analysis_user_created (user_id, created_at)` — supports `SELECT ... WHERE user_id = ? ORDER BY created_at DESC` (`listAiAnalysisHistory`).

### `ai_preferences` — per-user AI settings

Backs the "AI preferences" tab in Settings. Read by `ai.controller.js` before every `POST /api/ai/analyze` call to steer the prompt (model tier, persona, detail level, custom instructions); written by `PATCH /api/ai/preferences`.

| Column | Type | Null | Key | Notes |
|---|---|---|---|---|
| `user_id` | CHAR(36) | No | PK, FK → `users(id)` | One row per user (no synthetic `id` — the user *is* the key) |
| `ai_model_tier` | VARCHAR(32) | No | | `DEFAULT 'flash'`. One of `flash`, `gpt-4o-mini`, `claude-haiku`, `deepseek-chat` — enforced at the API layer (zod `enum`, `AI_MODEL_TIERS` in `aiPreferences.service.js`), not a SQL `CHECK`/`ENUM` constraint |
| `ai_persona` | VARCHAR(32) | No | | `DEFAULT 'balanced'`. One of `balanced`, `conservative`, `growth`, `income` (`AI_PERSONAS`) |
| `ai_detail_level` | VARCHAR(16) | No | | `DEFAULT 'concise'`. One of `concise`, `detailed` (`AI_DETAIL_LEVELS`) |
| `custom_instructions` | VARCHAR(1000) | Yes | | Free-text steering appended to the prompt, e.g. "Focus on ASX-listed stocks". `NULL`/empty both mean "no custom instructions" (API layer normalizes to `""` on read) |
| `created_at` | TIMESTAMP | No | | `DEFAULT CURRENT_TIMESTAMP` |
| `updated_at` | TIMESTAMP | No | | `DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP` |

- **Primary key:** `user_id` (also the FK — enforces exactly one preferences row per user).
- **Foreign key:** `user_id` → `users(id)` `ON DELETE CASCADE`.
- **Upsert pattern:** `updateAiPreferences()` uses `INSERT ... ON DUPLICATE KEY UPDATE` on `user_id`, so the first `PATCH` implicitly creates the row — there is no separate "create preferences" step.

---

## Relationships

```
users (1) ──< ai_analysis   (one user has many saved analysis runs)
users (1) ──1 ai_preferences (one user has exactly one preferences row)
```

Both tables reference `users(id)` with `ON DELETE CASCADE`, so deleting a user's account (`DELETE /api/auth/me`, or an admin hard-delete) automatically cleans up their AI analysis history and preferences along with the rest of their owned data.

## Ownership note

`ai_analysis` and `ai_preferences` are both fully owned and written to only by this feature — no other person's code reads or writes them. They both hang off `users(id)`, whose table definition lives in the shared `server/src/db/schema.sql` (created collaboratively — see that file's inline ownership comments per column). The full, system-wide ER diagram is the group's shared artefact in `design/er-diagram.md`.

## `users` — Google OAuth columns (migration 014)

"Sign in with Google" doesn't introduce a new table; it extends the existing shared `users` table with two changes, both in `server/src/db/migrations/014_add_google_oauth.sql` (and mirrored directly in `schema.sql` for fresh installs):

| Column | Type | Null | Key | Notes |
|---|---|---|---|---|
| `google_id` | VARCHAR(255) | Yes | UNIQUE | The stable Google account id (`sub` claim). `NULL` for password-only accounts. Set the first time a user signs in with Google — either on a brand-new row, or written onto an existing password account that shares the same (Google-verified) email. See `auth.service.js`'s `findOrCreateGoogleUser()`. |
| `password_hash` | VARCHAR(255) | **Yes** (was `NOT NULL`) | | Relaxed to nullable. A Google-only account (no `google_id` match *and* no matching-email password account existed) is created with `password_hash = NULL` — there's nothing to hash since Google is its only way to authenticate. |

- **Why not a separate `google_id` on its own table?** One Google account maps to exactly one app account, same cardinality as `email` — a column on `users` with a `UNIQUE` constraint is the simplest way to enforce "a given Google identity can only ever be linked to one account" at the database level, same reasoning as `email UNIQUE`.
- **Backward compatibility:** every pre-existing row keeps `google_id = NULL` and its existing `password_hash` — nothing about password login changes. The migration is idempotent (checks `information_schema` before altering), same pattern as the other numbered migrations in this directory.
- **Edge case not yet covered:** account-deletion/password-change re-confirm the current password (`authService.verifyPassword`) before proceeding — a Google-only account (`password_hash = NULL`) has no password to re-confirm with, so those two flows are not yet reachable for a Google-only user. Out of scope for this pass; would need a "set a password" flow first.
